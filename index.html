the basics of fox32

- alex winston, august 1st, 2026

hello! this fox32 tutorial series will mainly focus on the bare metal, meaning usage of the OS will be quite limited... instead, this tutorial will mostly focus on using the ROM, accessing hardware directly, etc... the tutorial will be using the fox32asm assembler syntax. for this tutorial, instruction encoding will not be covered in detail.

this tutorial assumes you already understand binary, hexadecimal, how bitwise operations work, etc... if you don't, perhaps it's good for you to read up on how those work before reading this.

basic stuff

the cpu has 32 32-bit general-purpose registers named r0 through r31. the processor is little-endian, and memory can be accessed in byte size (8-bit, 0..255/0xFF), half size (16-bit, 0..65535/0xFFFF), and word size (32-bit, 0..4294967295/0xFFFFFFFF).

nearly all instructions can take a size, suffixed with .8, .16, or .32. if left unspecified, the assembler will default to .32 size. some opcodes only take a .32 size, and therefore other sizes cannot be used with those opcodes.

instructions are 2 bytes minimum when assembled, and are formatted opcode<.8/.16/.32> <target>, <source>, where target and source can be one of 4 addressing modes:

  • register: r0 (this uses a register as the operand)
  • register pointer: [r0] (this uses the value at the memory address pointed to by register as the operand: M[r0])
  • immediate: 0xB00B135 (this uses a direct value as the operand)
  • immediate pointer: [0xB00B135] (this uses the value at the memory address pointed to by the direct value as the operand: M[0xB00B135])

additionally, if the operand is a register pointer, it can optionally be followed by an unsigned 8-bit offset: [r0+69], [r0+255]

mov, movz

the mov (MOVe) instruction is perhaps the simplest instruction to understand. it simply moves the source operand into the target operand:

    mov r0, 1337

the above piece of code simply moves the value 1337 into register r0. of course, as mentioned before, this actually assembles to mov.32 r0, 1337 because the size was left unspecified. the result is that this instruction will assemble into 7 bytes. this is usually not a concern, as we have 64MB of memory at our disposal, but this may not be very space-efficient, especially if you engage in sizecoding activities ;). the value 1337 can fit into a half (16 bits), thus, we can rewrite it as such:

    mov.16 r0, 1337

this will assemble into 5 bytes, 2 bytes less than our previous example. the saving may seem small, but these savings add up and may potentially give you space to do other things, which is important if you're writing a 512-byte program in the boot sector. you can also do the same thing with 8-bit values:

    mov.8 r0, 8 ; this will only assemble to 4 bytes

it is important to note that mov moves without clearing any data that was there prior. in particular, mov.8 and mov.16 will move the operand into lower half of the register if a register is specified as the target. in other words:

  • r0 contains the value 0xDEADBEEF
  • we execute mov.8 r0, 0x78
  • r0 now contains the value 0xDEADBE78
  • we execute mov.16 r0, 0x5A5A
  • r0 now contains the value 0xDEAD5A5A

this behaviour may not be desirable, especially if you are utilising the above techniques to reduce code size. to this end, there is the movz (MOVe Zero-extended) instruction. this instruction is the same as mov, but has the behaviour of clearing the upper bits (or in other words, the bits we don't care about) to 0:

  • r0 contains the value 0xDEADBEEF
  • we execute movz.8 r0, 0x78
  • r0 now contains the value 0x00000078

and the same for movz.16:

  • r0 contains the value 0xDEADBEEF
  • we execute movz.16 r0, 0x5A5A
  • r0 now contains the value 0x00005A5A

add, sub, inc, dec

before reading this, it is important to know that the CPU has 2 internal flags (which you cannot set manually under normal circumstances): zero flag, and carry flag. zero flag is set when a math or bitwise operation results in a value of 0. the carry flag, however, is set when an arithmetic operation results in an underflow/overflow. it is a bit of a misnomer, because the carry flag acts more like a borrow flag when doing subtraction, and it is not affected by any bitwise instruction. however as all official documentation refers to it as a carry flag, it will be referred to as the carry flag for simplicity.

the add instruction will simply add the number from the source operand into the destination operand; the source operand will remain unchanged (arithmetic operations here are in hexadecimal):

  • r0 contains 0x00001000; r1 contains 0x00000080
  • we execute add r0, r1
  • r0 contains 0x00001080; r1 contains 0x00000080

the above operation can be simplified into add r0, 0x80, freeing up a register. this (and the above information) applies to sub (SUBtract), only with subtraction rather than addition.

when using arithmetic instructions, it is important to remember that the size will affect your results (i.e it will only operate on that many bits). for example:

  • r0 contains 0x00000080
  • we execute add.8 r0, 0x80
  • r0 contains 0x00000000(!!) instead of the expected 0x00000100; r0 has overflowed

if the resulting value is too large to fit in a 32-bit register (or too large to fit in the operation size), it will either overflow or underflow. in both cases, the carry flag will be set.

the inc (INCrement) and dec (DECrement) are specialised cases of add and sub, respectively, but their source operand is fixed to an immediate type, and only allows values of 1, 2, 4, and 8.

why would we need this? we can just write add r0, 1 and be done with it. we can of course write it that way, but the difference is in size: add r0, 8 (with the default .32 operation size) assembles into 7 bytes (smaller operation sizes mean smaller assembly, but for reasons mentioned above, may have an undesirable effect on math operations). meanwhile the equivalent inc r0, 8 only assembles into 3 bytes, a ~42.8% decrease in size, and is massively helpful in saving space!

bse, bcl, not, and, or, xor

these instructions are bitwise instructions, and require a little understanding about how boolean algebra works. the simplest instruction is bse (Bit SEt) and bcl (Bit CLear), which set and clear a bit in the target operand, with the bit to set/clear specified by the source operand:

  • r0 contain 0b00000001
  • we execute bse r0, 4 to set bit 4 of r0
  • r0 now contains 0b00001001
  • we execute bcl r0, 0 to clear bit 0 of r0
  • r0 now contains 0b00001000

it should be noted that immediate types for the bse and bcl instructions are always 8 bits, and will always assemble to a fixed size of 4 bytes at minimum no matter the operation size (bse.8, bse.16, bse.32 will assemble to 4 bytes at minimum). the only effect then that the operation size has on bse and bcl is that immediate values larger than the size are ineffective (bse.8 r0, 16 will not set bit 16 of r0, for example).

bse, bcl, as well as bts count bits from the lowest bit:

    0101 0101
    |       ^--- bit 0
    +----------- bit 7

the not, which performs a bitwise NOT on the target operand, which just inverts every bit in the target operand (0 -> 1 ; 1 -> 0):

  • r0 contains 0b11001010
  • we execute not r0
  • r0 now contains 0b00110101
    1100 1010 (0xCA)
    |||| |||| 
    VVVV VVVV (0 -> 1 ; 1 -> 0)
    0011 0101 (0x35)

as always, the not instruction is affected by the operation size, so not.8 will only perform the bitwise NOT on the lower 8 bits of the operand, and not.16 only on the lower 16 bits. this also applies to every instruction in this section. it will not work on immediates, because the resulting syntax not.8 0x80 is nonsensical.

the and instruction performs a bitwise AND on the target operand with the source operand. in other words, it takes 2 bits in, and outputs a 0 if one of the inputs is 0:

  • r0 contains 0b11110101
  • we execute and r0, 0b00001111
  • r0 now contains 0b00000101
    1111 0101 (0xF5)
AND 0000 1111 (0x0F)
    ---------
    0000 0101 (0x05)

the or instruction performs a bitwise OR on the target operand with the source operand. in other words, it takes 2 bits in, and outputs a 1 if any of the inputs is 1:

  • r0 contains 0b11110001
  • we execute or r0, 0b00001111
  • r0 now contains 0b11111111
    1111 0001 (0xF1)
OR  0000 1111 (0x0F)
    ---------
    1111 1111 (0xFF)

the xor instruction performs a bitwise XOR (eXclusive OR) on the target operand with the source operand. in other words, it takes 2 bits in, and outputs a 1 if ONLY one of the inputs is 1 - the difference between XOR and OR is that if both inputs are 1, XOR outputs a 0:

  • r0 contains 0b11110001
  • we execute xor r0, 0b10101111
  • r0 now contains 0b01011110
    1111 0001 (0xF1)
XOR 1010 1111 (0xAF)
    ---------
    0101 1110 (0x5E)

sla, sra, srl, rol, ror

there are 3 bit-shifting instructions: sla (Shift Left Arithmetic), sra (Shift Right Arithmetic) and srl (Shift Right Logical). just like bse and bcl, immediate values are fixed to 8 bits. they are basically what it says on the tin: they shift bits in the target operand by the value in the source operand. take this example of sla, that shifts the target operand left by the value in the source operand:

  • r0 contains 0b10110011
  • we execute sla.8 r0, 1
  • r0 now contains 0b01100110
    +----------- this bit is discarded
    |
    1011 0011 
    //// ///
    |||| |||
    0110 0110 <- shift a 0 into here

the sra and srl instructions are mostly the same, they shift the bits in the target operand right by the value in the source operand. the difference is sra is an arithmetic left shift, meaning the sign bit will be duplicated into the bit next to it:

  • r0 contains 0b10110011
  • we execute sra r0, 1
  • r0 now contains 0b11011001

compare this to srl:

  • r0 contains 0b10110011
  • we execute srl r0, 1
  • r0 now contains 0b01011001
(srl)
    1011 0011 <- this bit is discarded
    \\\\ \\\
     |||\|||
    0101 1001
    ^----------- shift a 0 into here
(sra)
    1011 0011 <- this bit is discarded
    |\\\ \\\
    ||||\|||
    1101 1001
    ^^---------- contents of sign bit shifted in

the rol (ROtate Left) and ror (ROtate Right) instructions are functionally similar to the sla and sra/srl instruction, but the discarded bit is shifted into the upper/lower bit:

  • r0 contains 0b00110011
  • we execute ror r0, 1
  • r0 now contains 0b10011001
    0011 0011--+
     || \|||   |
     \\\ \\\   |
    1001 1001  |
    ^----------+
  • r0 contains 0b10110011
  • we execute rol r0, 1
  • r0 now contains 0b01100111
    +----------+
    |          |
    1011 0011  |
     ||| ||||  |
     |||/ |||  |
    //// ///   |
    |||| |||   |
    0110 0111<-+

mul/imul, div/idiv, rem/irem

the mul (MULtiply) and imul (Integer MULtiply) instructions are used to... well, multiply. the difference is that mul is an unsigned multiplication and imul is a signed multiplication. this has no noticeable effect on the final result, but affects how the carry flag is set.

for mul (unsigned):

  • r0 contains 0xFFFFFFFF
  • we execute mul r0, 0x02
  • r0 now contains 0xFFFFFFFE; carry flag is set, as the operation caused an unsigned overflow: 4294967295 * 2 > 4294967295

compare this to imul (signed):

  • r0 contains 0xFFFFFFFF (-1)
  • we execute imul r0, 0x02
  • r0 now contains 0xFFFFFFFE (-2); carry flag is cleared, as the operation did not cause a signed overflow: -1 * 2 = -2, which fits inside a signed 32-bit value

the div (DIVide) and idiv (Integer DIVide) instructions are also used to divide unsigned values and signed value, respectively. however, unlike mul/imul, the sign of the operation affects the final result. this also applies to rem (REMainder) and irem (Integer REMainder). unlike the rest of the math operations available, div/idiv and rem/irem do not affect the carry flag, therefore they only affect the zero flag.

for div (unsigned):

  • r0 contains 0xFFFFFFFF (4294967295)
  • we execute div r0, 10
  • r0 now contains 0x19999999 (4294967295 / 10 ~= 429496729)

for idiv (signed):

  • r0 contains 0xFFFFFFFF (-1)
  • we execute idiv r0, 10
  • r0 now contains 0 (-1 / 10 ~= 0)

wait! why did it return a 0? -1 / 10 should be a -0.1! this is because div/idiv throws away the fractional part, leaving only the integer part. this is important behaviour to remember, as there is no floating point support on fox32!

the rem/irem instructions are relatively simpler, as they always return an integer with no fractional part, so their result only depends on the sign of the operation.

for rem (unsigned):

  • r0 contains 0xFFFFFFFF (4294967295)
  • we execute rem r0, 10
  • r0 now contains 0x00000005 (the remainder of (4294967295 / 10) is 5)

for irem (signed):

  • r0 contains 0xFFFFFFFF (-1)
  • we execute irem r0, 10
  • r0 now contains 0xFFFFFFFF (the remainder of (-1 / 10) is -1)

the stack, push, pop

the stack pointer is located in the register rsp, and grows downward as values are pushed. push will push a new value onto the stack and decrement rsp. pop will pop a value off the stack and increment rsp. the amount that rsp is incremented or decremented by depends on operation size.

note: rsp does not enforce any alignment! therefore, rsp can be unaligned and values can still be pushed and popped normally.

    push.8  69           ; push 1 byte onto the stack
    push.16 1616         ; push 2 bytes onto the stack
    push.32 76768        ; push 4 bytes onto the stack
    ; rsp at this point is rsp+7
    pop.32  r0           ; pop 76768 into r0
    pop.16  r1           ; pop 1616 into r1
    pop.8   r0           ; pop 69 into r0

another behaviour to consider is that pop will not zero-extend, therefore any residual data in wherever you popped to will remain:

  • the last value pushed to stack was 0x45
  • r0 contains 0xDEADBEEF
  • we execute pop.8 r0
  • r0 now contains 0xDEADBE45

jmp/rjmp, loop/rloop, call/rcall, ret, rta

these instructions affect program flow, and apart from ret, they can take an absolute operand (jmp, loop, call) or they can take a relative operand that points to the instruction to jump to, indicated by an r for Relative (rjmp, rloop, rcall). relative instructions can also take an operation size (.8/.16/.32), while absolute instructions can only take a 32-bit size.

jmp (JuMP) loads the source operand into rip, the instruction pointer:

  • rip contains 0x03DC805A
  • we execute jmp 0x03FF8000
  • rip now contains 0x03FF8000

rjmp (Relative JuMP) adds the source operand into rip:

  • rip contains 0x03FF8000
  • we execute rjmp 3
  • rip now contains 0x03FF8003
  • we execute rjmp -7
  • rip now contains 0x03FF7FFC

loop decrements r31, and if it is not zero, it loads the source operand into rip (the relative equivalent rloop adds the source operand to rip instead). otherwise, the loop is terminated and execution continues to the next instruction. it is quite useful in making quick and easy loops:

    movz.16 r31, 16384 ; repeat 16384 times
_0:
    ; do something here
    loop    _0

the loop above will repeat 16384 times. internally, it decrements r31 first before it does the zero-check, and it will do this until the register is 0, at which point the loop terminates. therefore, it will count from 16383 down to 1.

call (and its relative counterpart rcall) is used for making subroutines and functions. when a call is encountered, the processor pushes the current rip to the stack as a 32-bit value, and loads (or adds for rcall) the source operand into rip. the old rip can be restored after the function is done with ret, which pops the last 32-bit value on the stack into rip.

    call subroutine
    ; do some stuff here
    ; ...
subroutine:
    ; do some more stuff here
    ret

you should take note to save the registers if you want to preserve all registers as-is by the time the subroutine has finished using push and pop.

rta (Relative To Absolute), while it does not affect program flow, is still important because it allows for true position independent code in conjunction with rjmp, rloop, and rcall. it takes a relative offset specified in the source operand, adds it into rip, and loads the final result back into the target operand. take this piece of code for example:

    org 0x800
    
    rta r0, some_data ; in the assembler, this translates to rta r0, 0x0C
    nop
    nop
    nop
    nop
some_data: data.8 0
  • we execute rta r0, some_data (rip contains 0x800 at this point)
  • r0 now contains 0x80C (rip+0x0C)

condition codes, cmp, icmp, bts

the fox32 architecture does not utilise separate conditional instructions unlike other architectures. it instead encodes the condition directly into the instruction, meaning instructions can be run predicatively, instead of jumping to another block of code to run the instruction. there are 6 condition codes (7 if you include always):

  • ifz - execute if zero flag is set. this condition is equivalent to "Equal To"
  • ifnz - execute if zero flag is not set. this condition is equivalent to "Not Equal To"
  • ifc/iflt - execute if carry flag is set. this condition is equivalent to "Lesser Than"
  • ifnc/ifgteq - execute if carry flag is not set. this condition is equivalent to "Greater Than or Equal To"
  • ifgt - execute if neither zero flag nor carry flag is set. this condition is equivalent to "Greater Than"
  • iflteq - execute if zero flag or carry flag is set. this condition is equivalent to "Lesser Than or Equal To"

this means that entire blocks of code can be written predicatively:

    cmp r1, 20
    iflteq ret

you should be careful when using arithmetic/bitwise operations, as those do modify the flags, meaning the original condition may be clobbered:

    mov r1, 21
    cmp r1, 20      ; r0 != 20, so zero flag is CLEARED
                    ; the next instruction will execute because zero flag is 0
    ifnz sub r1, 21 ; this will SET the zero flag, because 21 - 21 = 0
    ifnz ret        ; thus, this ret will not execute, because the zero flag was clobbered by the instruction above it

the cmp (CoMPare) instruction compares the target operand with the source operand and sets the carry flag and zero flag accordingly. internally, it determines how to set the carry and zero flag like this:

carry = (source_operand > target_operand);
zero = (target_operand == source_operand);

it can be thought of doing a subtraction operation, only that the result is not written back, it only affects the carry and zero flags.

icmp (Integer CoMPare) is just a signed version of the cmp instruction, which affects how the flags are set.

for cmp (unsigned):

  • r0 contains 1
  • we execute cmp r0, 0xFFFFFFFF (4294967295)
  • the carry flag is set, because 4294967295 is larger than 1

for icmp (signed):

  • r0 contains 1
  • we execute cmp r0, 0xFFFFFFFF (-1)
  • the carry flag is cleared, because -1 is NOT larger than 1

bts (Bit TeSt) will test a specific bit (specified by the source operand) in the target operand. what this actually means is that it just loads an inverted copy of that bit into the zero flag:

  • r0 contains 0b00010000
  • we execute bts r0, 4
  • bit 4 is copied into the zero flag. the zero flag is cleared, because bit 4 was set to 1.
